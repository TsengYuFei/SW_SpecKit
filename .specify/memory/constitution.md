# 課堂搶答系統 Constitution

## Core Principles

### I. PlantUML 設計優先（Diagram First Development）

- 每項功能及改變流程、互動、狀態或介面契約的變更，必須在實作前建立或更新 PlantUML
  設計圖，並在 Spec Kit 的規劃階段完成審查。實作任務必須能對應到已審查的圖或圖中情境。
- 必須依變更選擇適合的圖型，呈現受影響的角色、系統互動、狀態與例外路徑。
  搶答流程的設計必須呈現同時送出、重複送出及逾時等相關情境。
- PlantUML 原始檔必須納入版本控制並可成功渲染。若實作過程發現設計須調整，
  必須先更新圖與受影響的設計文件並重新審查，再繼續相關實作。

### II. 程式碼品質與可維護性

- 程式碼必須有明確的模組責任與可理解的命名。相同的業務規則必須共用同一實作，
  避免搶答判定或狀態轉換因重複實作而產生差異。
- 變更必須通過程式碼審查及專案已設定的格式、靜態檢查和測試。
  若變更既有行為，必須在規格與測試中記錄預期差異。

### III. 輸入驗證與錯誤處理

- 伺服端必須在執行業務邏輯前驗證外部輸入，包括必要欄位、型別、格式、長度或範圍，
  並依操作檢查權限和當前狀態。前端驗證可提供即時回饋。
- 無效或失敗的請求必須回傳可辨識的錯誤，並維持資料及搶答狀態一致。
  對外訊息必須提供足以理解或修正問題的資訊，且必須排除機密與內部堆疊資訊。

### IV. 功能與邊界測試

- 每個功能必須有正常情況和適用的特殊情況的自動化測試。測試必須檢查預期結果，
  並在涉及狀態的情況下驗證狀態是否正確更新或維持一致。
- 必須依功能納入無效輸入、邊界值、重複操作、逾時與併發等適用案例。
  搶答順序與結果判定必須有涵蓋同時及重複送出的整合測試。
- 合併前必須執行受影響的測試，並在審查紀錄記下測試指令與結果。

### V. 文件一致性與 AI 產出審查

- AI 產生或修改的文件必須由人工審查。審查人必須以實際程式碼、設定、
  測試結果或可重現的操作結果核對文件中的系統行為。
- 功能變更影響既有說明時，必須在同一變更同步更新相關規格、PlantUML 圖與操作文件。
  尚未實作的行為必須在文件中標示為預定設計。

### VI. 機密資料保護

- 密碼、API Key、權杖及其他機密值禁止直接寫入程式碼、文件、日誌或其他紀錄，
  包括測試資料、範例、錯誤訊息與審查紀錄。
- 應用程式所需的機密值必須在執行時透過環境變數或機密管理服務注入。
  文件與測試只能使用設定名稱或無效的示範值。

## 安全與紀錄要求

- 寫入日誌、錯誤報告或其他診斷紀錄前，必須移除或遮蔽敏感欄位，
  包括請求標頭、請求本文及例外訊息中的機密值。
- 發現機密外洩時，必須撤銷或輪替受影響的機密，並清理洩漏的副本。
  處理紀錄必須記載影響範圍與處置結果，且排除機密值。

## Spec Kit 開發流程與審查

1. 規格階段必須定義功能、可驗收的正常情況與特殊情況。
2. 規劃階段必須依原則 I 完成相關 PlantUML 設計與審查，再開始相關實作。
3. 任務階段必須納入實作、測試及適用的圖與文件同步工作。
4. 合併前，審查人必須檢查適用的原則、PlantUML 圖的渲染與一致性、測試結果、
   AI 產出文件的人工核對，以及變更內容是否含有機密值。發現缺失必須修正後方可合併。

## Governance

- 本憲章為本專案的開發與審查依據。每項變更都必須在審查時核對適用條文。
- 修訂提案必須記錄變更理由、影響範圍與生效日期，由專案維護者審核通過後生效。
  若影響既有工作，提案必須提供調整計畫，並同步更新受影響的規格、設計或流程。
- 憲章採語意化版本。移除或不相容地改寫原則時升主版本（MAJOR）。
  新增原則、章節或實質擴充要求時升次版本（MINOR）。
  僅釐清文字或修正錯字時升修訂版本（PATCH）。
